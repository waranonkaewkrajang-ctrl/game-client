# ถ่ายทอดสดฟุตบอล: Logic และขอบเขตที่ตรวจสอบได้

หน้าใหม่ `/live` — วันที่ 10 พฤศจิกายน 2026

ดีไซน์ล่าสุด: ผู้ชมเห็นการ์ดคู่สดแยกตามลีกก่อน มีโลโก้/VS/สกอร์/ปุ่มดูถ่ายทอดสด แล้วจึงเปิด iframe ของคู่ที่เลือก เมื่อเริ่มดูแล้วเท่านั้นจึงใช้ auto-next ปุ่มกลับไปเลือกคู่ปิด iframe และหยุด auto-next จนเลือกดูใหม่ ลบ footer แหล่งข้อมูลและเวลาตรวจจากหน้าลูกค้าแล้ว

## สิ่งที่ทำ

```text
Worker ทุก 10 วินาที (แม้ไม่มีผู้ชม)
   ↓
GET /api/live-football → cache + single-flight → AMB live feed
   ↓                                        ↓
รายชื่อทุกคู่ที่กำลังสด                  คู่หายจากรายการ
   ↓                                        ↓
หน้า /live อัปเดตรายชื่อ/สกอร์      ตรวจหายอย่างน้อย 2 รอบ + detail API
   ↓                                        ↓
POST /api/live-football/prepare           ยืนยันจบแล้ว
(คิวเบื้องหลังอัตโนมัติรายผู้ชม)             ↓
   ↓                                  เปิดคู่สดถัดไปอัตโนมัติ
URL ตัวเล่นหลายคู่พร้อมก่อนเลือก ←───────────┘
   ↓
กดคู่ใด = เปลี่ยน iframe.src จาก URL ที่ได้รับไว้แล้ว
```

## แยกส่วนให้ถูกต้อง

- รายการที่แสดงเป็นทุกคู่จาก `soccer/live` ที่ผ่านการตรวจรูปแบบ ไม่มีรายชื่อจำลองหรือกำหนดเอง รายการนี้ไม่ใช่บอลทุกแมตช์ทั่วโลก แต่เป็นคู่ที่ AMB เปิดสตรีมให้ ณ เวลานั้น
- Worker ดึงข้อมูลรายการตลอด ส่วน URL ตัวเล่นเตรียมล่วงหน้าแยกรายผู้ชม เพราะมีข้อมูลเซสชัน/IP/เวลาใน URL ไม่แชร์ URL เดียวให้ทุกคน
- คิวเตรียมลิงก์ทำงานเองตั้งแต่เปิดหน้า ทุก 5 วินาที จัดครั้งละ 4 คู่ พร้อมกันไม่เกิน 2 คำขอ และไม่เกิน 4 คำขอรวมต่อ process คิวเดินต่อไปทุกคู่โดยไม่ต้องกดดู ไม่มีตัวกรองจำกัดลีกดัง
- หน้าลูกค้าไม่มีข้อความ “เตรียมตัวเล่น/เตรียมสัญญาณ” ไม่มีรายละเอียดขั้นตอนภายใน แสดงเฉพาะคู่สด สกอร์ ลีก และตัวเล่น
- ปุ่มเลือกคู่ไม่เรียก API หาลิงก์ การดาวน์โหลดวิดีโอ/handshake ของ iframe ยังคงเกิดเมื่อเปิดคู่ตามธรรมชาติของ player การขอ URL ล่วงหน้าไม่ได้หมายความว่าโหลดไฟล์วิดีโอทุกคู่พร้อมกัน
- การขอ URL ยังใช้เวลาเครือข่ายจริง ระหว่างการเชื่อมครั้งแรกหรือเมื่อแหล่งล้มเหลว ไม่สามารถรับประกันเปิดทุกคู่ได้ทันทีโดยไม่มี buffering

## เปลี่ยนคู่เมื่อจบ

1. คู่ยังอยู่ใน feed → `live` เปิดคู่เดิมต่อ รายชื่อ/สกอร์เปลี่ยนไม่ remount iframe
2. คู่หายไปจาก feed ที่ตอบสำเร็จ → `checking` เก็บวิดีโอเดิมระหว่างตรวจ แต่ไม่เสนอเป็นคู่สดใหม่ในรายการ
3. หายอย่างน้อย 2 รอบ → สอบถาม `/match/soccer/{id}` หมุนตรวจครั้งละไม่เกิน 4 คู่เพื่อไม่ให้คู่ท้ายคิวถูกทิ้ง
4. ยืนยันจบจาก `FT/AET/...`, `results: null`, หรือรูปแบบที่ตรวจพบจริง HTTP 200 `{ "message": "OK" }` โดยไม่มี results → `ended`
5. ถ้าเปิด auto → เลือกคู่แรกในลำดับ feed ที่ยัง `live` และมี URL ที่ยังใหม่ ไม่มี URL ที่พร้อมก็รอให้คิวเบื้องหลังทำงาน ไม่เปิดคู่ที่จบแล้ววนซ้ำ
6. ถ้าไม่มีคู่สด → แสดงรอคู่ถัดไป เมื่อคู่ใหม่เข้ามาและเชื่อม URL ได้ จะเริ่มเอง
7. ปิด auto → เมื่อคู่จบหยุดให้เลือกเอง ไม่ไปหา URL ตอนคลิก
8. API ผิดพลาด/รูปแบบ JSON เปลี่ยน → เก็บข้อมูลล่าสุดและแจ้งขัดข้อง ไม่ตีความว่าทุกคู่จบ

## URL และสถานะภาพ

- เก็บ URL ในหน่วยความจำและตอบ `private, no-store`; cookie แยกเฉพาะระบบถ่ายทอดสดเป็น HttpOnly/SameSite=strict ไม่ใช่ cookie หรือ token ของ Login
- นโยบาย local refresh 90 วินาที เริ่มขอใหม่ก่อนหมดรอบ 20 วินาที เป็นค่าที่เราเลือก ไม่ใช่อายุ token ที่ผู้ให้บริการรับรอง
- URL ใหม่ที่เข้ามาไม่เปลี่ยน iframe ของคู่ที่ดูอยู่กลางคัน
- อนุญาตเฉพาะ HTTPS โดเมนตัวเล่นที่ตรวจพบและ path `/livetv/` ไม่รับ URL arbitrary จากผู้ใช้
- iframe ต่างโดเมนทำให้ JavaScript ของเว็บเราอ่าน `video.ended`/`currentTime` ไม่ได้ จึงใช้ข้อมูลการแข่งขันเป็นสัญญาณเปลี่ยนคู่ ไม่ใช้ iframe onload เป็นหลักฐานว่าภาพกำลังเล่น
- ยังไม่มีเอกสาร postMessage events ของ GLIVE จึงไม่สร้าง event จบวิดีโอขึ้นเอง
- ไม่มีการแกะ token, ปลอม Origin/Referer, media relay หรือดาวน์โหลดไฟล์วิดีโอผ่าน server เรา

## การรัน Worker

```powershell
node scripts/live-football-worker.mjs
```

ค่าเริ่มต้นติดตาม Next.js ที่ `http://127.0.0.1:3000` กำหนด `LIVE_FOOTBALL_APP_ORIGIN` ให้ตรงแอปเมื่อนำขึ้นโฮสต์จริง

Worker เป็น process แยก ไม่ใช่การ restart Next.js เมื่อ deploy ต้องจัดให้ process นี้เริ่มอัตโนมัติและกลับมาทำงานหลังเครื่องบูตตามระบบโฮสต์จริงด้วย ส่วนหน้า /live ยัง polling เองได้หาก worker ไม่รัน แต่จะไม่อัปเดตขณะไม่มีผู้ชม

Cache/คิวในเวอร์ชันนี้อยู่ใน process memory รองรับการทดลองหนึ่ง instance ไม่ใช่ durable queue หรือ cache ร่วมหลายเครื่อง หาก deploy หลาย instance ต้องเพิ่ม shared store/queue และกำหนดความจุ/rate limit ตามผู้ให้บริการ

## ผลทดสอบ

- ทดสอบ API จริงได้ 2 คู่ และขอลิงก์ล่วงหน้าทั้งสองคู่สำเร็จ HTTP 200, pending 0
- ต่อมาคู่โบลิเวียหายไปและ detail API ตอบ `{ "message": "OK" }` จึงแก้การตรวจจบตาม response จริง คู่เม็กซิโกยังสด
- หน้า /live เปิดคู่เม็กซิโกอัตโนมัติ ภาพจริง 960×540, readyState 4, paused false
- ตรวจรอบสุดท้าย video.currentTime เดินถึง 195 วินาที และ iframe URL เดิมคงอยู่ระหว่างอัปเดตข้อมูล/ค้นหา/สลับปุ่ม auto
- ตรวจหน้าจอ 1440px, 390px และ 320px ไม่มีแนวนอนล้นจอ; หน้าลูกค้าไม่มีคำว่า “เตรียม”
- TypeScript, ESLint เฉพาะไฟล์ใหม่ และ behavioral tests 5 รายการผ่าน; CSS parse ผ่าน ไม่มี selector/property ซ้ำใน scope เดียวกัน
- สถานการณ์หลายคู่/เปลี่ยนเมื่อจบ/API ล่ม/URL หมดรอบ/แยก session ทดสอบออฟไลน์ใน `scripts/test-live-football.cjs` ไม่แทรกคู่ทดสอบในหน้าลูกค้า
- ต้องทดสอบ public IP ของ production กับผู้ชมต่างเครือข่ายก่อนเปิดจริง URL อาจมีการผูก IP ตามรูปแบบที่พบ และต้องตรวจขอบเขตสิทธิ์ใช้สตรีมของบัญชีผู้ให้บริการ
